## 任务 1 · 修卡死 + 换图标

### 卡死的原因（已定位，证据在下面）

**主进程被同步目录遍历堵死。** Electron 的窗口消息循环由主进程持有，主进程一卡，
Windows 就画出那个「抱一 未响应」对话框 —— 截图里就是这个。

热点在 `electron/kinds/software/tools.ts`：

- `countExes()` 是**全同步**的 `fs.readdirSync` 递归下钻（`COUNT_MAX_DEPTH = 3`，
  `COUNT_MAX_ENTRIES = 3000`）。
- `listDirectory()` 对**每一个子目录**都调一次 `countExes`，子目录上限
  `LIST_LIMIT = 120`。
- 最坏一次 `list_directory` 工具调用 = 120 × 3000 = **36 万次同步目录项访问**，
  全在主线程上。
- `aiService.ts` 的 `CONCURRENCY = 3`，三个 agent 的工具调用在单线程上排队叠加。

这也解释了用户描述的「关掉重开后识别结果已在数据库里」：后台一直在跑，只是界面
被堵住了刷不出来，进度停在 `0/15`。

**已排除的两个怀疑方向**（别再回头查）：

- ~~IPC 消息堆积~~ —— `aiService.ts` 的 `makeReporter()` 已经有 150ms 节流。
- ~~渲染进程自己卡~~ —— `src/composables/useAI.ts` 的进度回调就是一句
  `progress.value = p`，不可能堵。

### 第二个症状还没解释

用户第二次测试是「**打开扫描界面就卡住**，关掉重开没有识别结果」。这跟上面那条
不是同一件事（那次还没开始识别）。开工时要查：`scan:units` / `listScanUnits()`
和扫描页 mount 时走的路径里有没有同步遍历。**先查清再动手**，别把两个症状按一个改。

### 图标读不到的原因（已定位）

`electron/services/iconExtractor.ts` 里 `app.getFileIcon` 拿不到图就
**静默返回 `''`**，三处失败分支都是空字符串，没有日志、没有重试。所以「部分软件
图标未读取到」是预期行为的暴露，不是 bug —— 这也正是用户要「手动换图标」的原因。

### 换图标做完之后记下来的两处

**1. 两套命名共处一个目录，靠形状分开。** 手动图标叫 `<条目 id>.<ext>`（UUID），
自动提取的叫 `<exe 路径的 sha1>.png`（40 位纯十六进制），撞不上。好处是
「这张图是不是用户亲手指的」直接从路径看得出来（`isManualIcon`），
**省掉一列 schema 和一次迁移**；而且 `extractIcon` 只认 sha1 那个名字，
手动图标不占它，所以两边互不挡路。

**2. `iconUrl` 从前没有 `?v=`，这次必须补。** `coverUrl` 早就有，注释也写明了理由：
文件名按 id 定，换一张之后 URL 一个字符都不变，Chromium 继续拿内存里那张旧图。
图标从前没这个问题是因为它**从来不会被替换**（sha1 命名 + 内容不变）——
换图标功能一上线，这个前提就没了。补法照抄封面：拿 `updated_at` 当版本号。
`baoyi://` 那个协议处理器本来就不看查询串，不用改。

### 要做的事

1. 把目录遍历改成不堵主线程：`fsp.readdir` 异步化 + 让出事件循环，
   或给 `countExes` 加缓存 / 收紧预算。改完主进程要能在扫描中途响应窗口消息。
2. 查清并修掉「打开扫描界面就卡住」。
3. 软件详情页加「更换图标」按钮，照抄游戏模块 `game:pick-cover` 那套：
   `dialog.showOpenDialog` → 拷进 app 数据目录 → 更新库 → 刷新界面。
   软件侧现在只有 `software:list/get/update/remove/counts/launch/reveal/add-manual`
   八个通道，**没有图标通道**，要新加。
   注意 `game:pick-cover` 的一个既有讲究：对话框的扩展名过滤器和真正执行校验的
   那份名单**共用一个来源**，不能分开写。
4. 四道闸门 → commit。

## 待确认（用户醒来拍板，不阻塞开工）

### A. hanime1.me 走的是公开页面还是私有密钥 API

任务 3 读代码时确认。**如果是公开 HTML 抓取**：只是多一条传输通道，没有逆出来的
凭据，按现有刮削器的样子写就行，任务 4 可以直接做。**如果是带硬编码
`api_key` + 签名的私有 API**：撞上 v0.7 里否掉 MoviePilot frodo 豆瓣通道的
同一条理由，那时候的结论是走用户自己配的搜索源。这种情况先在计划里记下来、
把解析器和分类入口那两半做掉（它们不依赖刮削），刮削那半等拍板。

### B. 分类名用 `hentai` 还是 `里番`

用户写的是 `category = 'hentai'`。但 `electron/kinds/video/taxonomy.ts` 里七个
分类的 `name` **全是中文**（`华语`/`欧美`/`日韩`/`动画`/`纪录片`/`综艺`/`其他`），
`id` 才是英文 slug（`video-cn`/`video-anime`…）。而分类名是**显示在侧边栏上给人
看的**，还能被用户改。

**打算按既有惯例做**：`id = 'video-hentai'`、`name = '里番'`，跟其余六个一致。
理解用户那句话的意思是「用 category 这一列做区分」，不是「这一列里必须存英文」。
醒来觉得不对再改，改动很小。

### C. 扫的时候怎么知道它是里番

任务 4 说「根据 category 自动选择刮削通道」，但分类本身是识别阶段由 agent 定的，
而刮削又发生在识别之后 —— 通道选择依赖分类、分类依赖识别，识别又要靠刮削拿数据，
这里有个环。

**打算这么破**：不靠 agent 猜，靠两个更硬的信号 ——（1）文件名形态本身就很有辨识度
（`＃2`、`ROUND1`、`[中文字幕]`、`_720P` 这组合），解析器命中就归里番；
（2）扫描根目录可以标成里番来源。两个都不命中时保持现状、不擅自归类。

### D. 里番分类和 6b 的 `user_edited` 保护怎么相处

Step 6b 的规则是「用户改过的字段重扫不覆盖」，`category` 在保护名单里。所以用户
手动把某部改出/改进里番之后，重扫不会改回去 —— **这是对的**，用户说了算。
但连带的是刮削通道也跟着变，重扫时会换一条通道去刮。这个行为要在计划里写明，
免得以后当成 bug 查。
