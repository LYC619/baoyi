## 二、贯穿全版本的硬约束

这几条不是风格偏好，破了会当场出问题。

### 1 · `kinds/game/` 下的逻辑只收 `SqlDb`

不 import `services/database.ts`。后者绑 electron + better-sqlite3（为 Electron ABI 编译，
纯 node 里加载不了），一旦引进来，这一层就只能在应用整个跑起来之后才验证得了。
自检靠 `node:sqlite` 驱动同一份 SQL。

`service.ts` 是唯一的例外，**也因此只做绑定和汇总，一条判断规则都不放**。这条约束是整个
版本能有 227 条自检的前提 —— 判断规则和 Electron 一旦缠在一起，就只能靠开应用点界面来验。

配套：自检能走到的文件，import 必须写显式 `.ts` 后缀。

### 2 · `categories` / `tags` 是全局单表，带 `kind` 维度

漏掉 kind 过滤，RPG 和魂系会进软件的识别 prompt，agent 会拿「RPG」去归类一个调试器。

### 3 · `save_backups` 刻意没有 `resource_id` 外键

级联删记录不会删磁盘上的文件，只会让用户再也找不到它们。

### 4 · 路由用 hash 模式

生产走 `file://`，history 模式起不来。

### 5 · 本地图片必须走 `baoyi://` 协议

打包后的 `file://` 页面里 `<img src="C:\...">` 加载不出来。这条在 Step 7 做封面时正式生效。

## 三、七步各自做成什么样（含偏离计划之处）

偏离本身比结论重要 —— 每一处都有理由，理由记在这里，免得下一轮把已经想过的事又想一遍，
或者把刻意的取舍当成漏洞去「修」。

### Step 1 · 模块切换栏 + 路由

`useModules.ts` 记当前 Tab、每模块最后路径、滚动位置；路由挂 `meta.module`，`afterEach` 记账。
新增 `npm run check-modules`（7 组断言）—— 模块记忆是这一步唯一有状态的逻辑。

**偏离**：游戏计数显示「—」不是「0」（表还没建，报 0 等于替不存在的表撒谎）；
`view_mode` 按模块分存没做（它是 `AppSettings` 的字段，而游戏视图要到 Step 4 才有，
拆开来没有第二个消费者）。规划书里提的 `tokens.css` 实际叫 `src/styles/variables.scss`。

### Step 2 · 数据层

规划书说「插入游戏内置分类和标签」，**照字面做会出事**：`categories` / `tags` 是全局单表，
`listCategories()` / `tagPool()` 直接喂给软件识别的 prompt。所以两张表加 `kind` 列，
`tags` 唯一键从 `name` 换成 `(kind, name)` —— 「单机」「开源」两个品类都用得上，
全局唯一会让先到的把词占死。`listCategories(kind = 'software')` 默认软件，
所以整条 IPC 和渲染链路一字没改。

顺带揪出三处同源越界（都是跨品类扫全表）：`renameTag` 重名检测会把游戏的「开源」并进软件的、
`replaceTagInEntries` 删游戏标签会抹掉软件条目上的同名标签、`pruneOrphanAiTags` 会把游戏
刚识别还没确认的标签清掉。

规划书写「迁移前自动备份（延续现有惯例）」—— 查下来**这个惯例不存在**，`.bak` 全是手工建的。
补上了：`VACUUM INTO` 出完整快照（不是 `copyFile`，那样会漏掉 WAL 里没落盘的事务），
同一旧版本只备一次，免得重试时把唯一那份好的盖掉。

回滚脚本第一版是错的，真库副本往返查出来的：只删了 `kind` 列，把游戏的 7 个分类 12 个标签
留在表里，退回 v5 之后 `listCategories()` 不带过滤，那些词会当场出现在软件侧边栏。
已修成连词表一起清。

**偏离**：`resource_types` 表没建 —— 品类注册是代码级的（`kinds/index.ts` 的 `KINDS`），
加一张表只是把同一份信息抄两遍。

### Step 3 · 扫描与识别

三处真机跑出来的改进：

1. `E:\游戏` 这种收纳目录被 `inspectDir` 当成「一个有 33 个 exe 的游戏」（收纳判断原先
   只在 `scanGameRoot` 里，直接调 `inspectDir` 绕过去了）。
2. 模型把苏丹的游戏的发行商猜成 `2P Games`（实际 `DoubleCross`），六次探测全打空，
   而答案就在 82 字节的 `<X>_Data\app.info` 里 —— 改成扫描时读出来一起进 prompt，
   第二次第一发命中。**能在本地读到的事实，不该让模型去猜。**
3. 补了 WeGame（`rail_files` / `TCLS`）和 QSP 两个指纹，以及「目录名去掉 `(appid)` 尾巴
   再对主程序」——「洛克王国：世界(2002304)」的卸载器体积是本体的三倍，按体积挑必错。

**偏离**：`search_cover` 没做（封面在规划书自己的优先级表里是 P2）；识别结果直接落库，
不走暂存确认面板（游戏一个目录一条，认错了在详情页改个名字就完了，为它造 `pending_game`
表加一屏 UI 不划算）—— 代价是模块切换栏那个「N 个待确认」角标永远不会亮。

### Step 4 · 主页与详情页

不补它，界面上没有任何按钮能触发 Step 3 的链路，游戏库永远是空的。

**偏离**：只有封面墙一种排布（游戏靠封面认，一行文字的列表把唯一的识别线索扔了）；

### Step 5 · 存档备份与还原

`services/fstree.ts` 是从 `organize/fsops.ts` **提**上来的公共层（目录树遍历、复制校验、
文件夹名规范、路径包含判断），不是新写的。

`kinds/game/backup.ts` 是引擎：备份走「复制 → 校验 → 才记账」，还原走「先自动备份当前存档
→ 复制到旁边校验 → 三次改名就位」。**每个失败点上磁盘都是一份完整存档。**
说明文件 `backup.json` 放在载荷 `save/` 外面 —— 放里面，还原会把它复制进用户的存档目录。

三处真机改掉的：

1. **单文件存档整个备不了**（`walkTree` 对文件 `readdir` 会抛）。更要紧的是还原那边判断
   「当前存档有没有东西」也只用它，异常被 catch 吞掉之后结论是「不用备份」——
   **单文件存档会被直接覆盖**，而这一步存在的全部理由就是给还原留退路。
2. `nestedInside` 只比 `\`，`D:/备份` 让护栏整个漏过去。
3. 裸盘符 `D:` 不是盘根而是「D 盘上的当前目录」。

**偏离**备份目录结构：计划是 `{根}/{游戏名}/save_{时间戳}/`，实做
`{根}/{游戏名}_{id6}/{时间戳}_{存档名}/` —— 同名游戏不打架，一个游戏多条存档路径也分得开。

## 四、存档发现的三层结构

这是整个版本技术含量最高的一块，最终形态是三层，缺任何一层都还能工作。

```
第一层  agent 推理     ── 读 app.info / 引擎指纹，按规则推
第二层  扫描器启发式    ── 五处常见位置
第三层  ludusavi 查表   ── 19258 条已知存档位置
```

### 第三层：ludusavi-manifest 编译进包

`scripts/build-save-manifest.ts` 在**构建期**把 `参考/ludusavi-manifest-master/data/manifest.yaml`
编译成 `resources/save-manifest.json`（输入 gitignore，输出入库），`electron-builder.yml` 的
`extraResources` 带进安装包。运行时 `kinds/game/savedb.ts` 查表，`tools.ts` 加
`lookup_save_paths` 工具，prompt 里排在五处启发式位置**之前**。

编译期就转成 JSON，是因为运行时不必带 YAML 解析器，而且 16.7 MB 解析要几百毫秒、
上百 MB 内存。编译期还顺手过滤，于是运行时可以假定索引里每条模板都展得开。

**这一层最要紧的一个教训**：第一版用「整条模板要么全展开要么丢掉」，结果把最有价值的
两条丢了 —— 艾尔登法环是 `<winAppData>/EldenRing/<storeUserId>`（Steam 数字 ID），
空洞骑士是 `…/Hollow Knight/*.dat`（通配符）。改成 `truncateTemplate()`：在第一个认不得的
段上截断、保留祖先目录。而祖先目录其实是**更好**的备份目标 —— `%APPDATA%\EldenRing`
一备就把所有档位都带上。

截断必须有下限，否则 `<winAppData>/<storeUserId>` 会塌成 `%APPDATA%` 本身，
把整个 Roaming 当成某个游戏的存档备走。

改完收进索引的从 18634 涨到 **19258**，其中 9798 条是截断来的。

最终编译统计：总条目 53050 / 带 files 22218 / 收进索引 19258（撞键合并 16）/ 截断 9798 /
丢弃·非存档 11207 / 丢弃·非 Win 6667 / 丢弃·截不出结果 2074 / **2.04 MB**。

索引缺失是**合法状态**（`saveDb` 可空）：查表是三层里的兜底一层，它不在时前两层照常工作。

已验证：`Sultan's Game` → `%LOCALAPPDATA%Low\DoubleCross\SultansGame\SAVEDATA` ——
正是 Step 3 里烧掉六次探测才找到的那个答案。

### 第一层：引擎通用规则（Step 7 补）

prompt 里原来只有「按位置猜」，查表落空之后模型就只能瞎试。新增 `ENGINE_SAVE_RULES` 一张表，
渲染进 prompt，顺序定成 **查表 → 按引擎推 → 按位置猜**：

| 引擎 | 游戏目录外 | 游戏目录内 |
|---|---|---|
| Unity | `%LOCALAPPDATA%Low\<公司名>\<产品名>` | |
| Unreal | `%LOCALAPPDATA%\<游戏名>\Saved\SaveGames`、`Documents\My Games\<游戏名>\Saved\SaveGames` | |
| RPG Maker | | `save\`、`www\save\` |
| GameMaker | `%LOCALAPPDATA%\<游戏名>` | |
| Ren'Py | `%APPDATA%\RenPy\<游戏名>` | `game\saves\` |
| Godot | `%APPDATA%\Godot\app_userdata\<游戏名>` | |
| KiriKiri | `%APPDATA%\<游戏名>` | `savedata\` |
| NW.js | `%APPDATA%\<游戏名>`、`%LOCALAPPDATA%\<游戏名>` | |
| QSP | | `save\`、`saves\` |

三个设计要点：

- 表是**数据**而不是散在 prompt 里的散文，所以自检能逐条校验它，prompt 和校验共用一份来源。
- **`where`（游戏目录外）和 `in_game`（游戏目录内）是两个独立字段**，不是一个布尔。
  第一版写成 `in_game_dir?: boolean` 被自检当场打回 —— Ren'Py 和 KiriKiri **两处都写**，
  一个布尔表达不了。这是**建模错误**，不是笔误，值得单独记一笔。
- `where` 里每一条展开后**必须落在 `scanner.saveRoots()` 白名单内**。写一条
  `%PROGRAMFILES%\Steam\userdata` 看着很有道理，但它不在白名单里，模型照着做只会
  白烧一次探测额度。自检守着这一条。

**不管路径从哪一步来，都必须过 `detect_save_path`。** 引擎规则给的是「该在哪」，
探测回答的是「这台机器上在不在」。prompt 里写死了「没验过就填等于编」，自检也钉住了这句话。

### 保留策略

`overRetention()` 只**回答问题**，一个字节都不删；删不删由 `Detail.vue` 的 `pruneOver()`
问过用户再做。上限按 **(游戏, 存档路径)** 配对算，不是按游戏 —— 一个游戏有两条存档路径时
各留各的。`0` 或不成立的值都当「不限」。清空输入框退回默认 10 而不是当成 0：
把手滑理解成「关掉提示」是不对的。

### 存档状态与失效标记

`SaveStatus = 'none' | 'unbacked' | 'backed'`，互斥且穷尽。筛选和侧栏计数共用 `db.ts` 里
同一份 `SAVE_WHERE` SQL —— 分开写迟早会漂，「侧栏说 3 个、点进去列 4 个」比没有这个功能
更糟，自检里专门有一条守这个。侧栏顺序把「未备份」排第一：三格里只有它有行动含义。

开库时 `checkAllSavePaths()` 扫一遍，**只读，不写库**。这一条偏离了计划的字面写法
（计划说「不存在的标记为路径失效」，字面读像是要写进记录）：外置硬盘没插、网络盘没连是
一时的，写进库就成了一个会过期却不会自己消失的判断。所以它是**进程内的瞬时状态**，
跟着这次会话消失。

失效**没有**折进那个三态枚举：它是正交的一维（有路径、可能也有备份，只是当下指不到），
塞进去会让三分变成含义重叠的四分。

## 五、游玩时长与状态

`kinds/game/session.ts` 是纯记账层（收 `SqlDb`，可自检），`service.ts` 管进程：
`spawn` + `detached` + `unref`，监听 `exit` 收一段。

**三件事分开判断，因为成立条件不同：**

- **总时长** 够门槛才加
- **上次游玩** 一律更新
- **游玩状态** 只做 `unplayed → playing` 这**一个**方向的翻转

状态只翻这一次，是因为「启动」这个动作能推出来的结论只有这一个。玩完算不算通关、
放下算不算搁置，只有用户知道，猜错了他还得回来改。

**60 秒门槛**（`MIN_SESSION_SEC`）：一大票游戏是启动器 exe 拉起本体然后自己退出，
我们监听到的退出发生在两三秒内。把那个记成「玩了 3 秒」，累积几十次之后总时长就是一句假话。
没计入时的文案要说清为什么（点出「启动器」），不能显示「已记录 0 分钟」——
那只会让人以为功能坏了。但那种情况下**照样**更新上次游玩、照样翻状态：他确实启动过。

`will-quit` 里 `finalizeGameSessions()` 排在 `closeDb()` **之前**收尾开着的那几段 ——
顺序是硬要求，所以写在同一个处理器里而不是两个 `app.on`（那就依赖注册顺序了）。

**刻意不建 sessions 表**：单次游玩历史现在没有任何界面要读，为它开表就得把 SCHEMA 推到 7
并写迁移和回滚 —— 为一个还没有消费者的数据付这个代价不划算。

不做后台监控 —— 用户直接双击 exe 玩的不记时长，这是规划书写明的取舍。

## 六、Step 7 收尾

### 关联文件管理

判断规则全在 `kinds/game/links.ts` 里（纯逻辑，自检能直接驱动）：类型猜测、去重、
上限 20、标签上限 20 字。`service.ts` 只做绑定。

- **`guessLinkType` 故意保守**：只有明确是文档的后缀（pdf/txt/md/chm…）才判成攻略，
  exe 一律落 `other`，不猜「修改器」。猜错类型比不猜更烦人 —— 用户得先发现它猜错了，
  再手动改回来。
- **能不能打开，只看在不在名单里。** `openGameLink` 先过 `hasLink()` 再碰 shell。
  这是渲染进程和「打开任意本地文件」之间**唯一的那道边界**，删掉它等于把 shell 开放给页面。
- **用户手加的路径不锁在游戏目录里**，跟 agent 那条路（`coerceLinkedFiles` 会沙箱化）
  刻意不同：agent 是在**猜**，猜出目录外的东西就是幻觉；用户是在**指**，人家的攻略本来
  就可能存在 D 盘另一个文件夹里。
- 选文件和选文件夹是两个按钮 —— Windows 的对话框没法一次同时选两种。

### 封面手动替换

走「加 `baoyi://cover/` 分支」这条路，**没有**把封面塞进 `iconsDir()`：
**图标是缓存**（`clearIcons()` 重置时整个目录一扫而空），**封面是用户亲手指的资产**，
共用一个目录等于下次清库把人家的封面顺手删了。所以新开 `coversDir()`，协议处理器从写死的
`hostname === 'icon'` 改成一张 `PROTOCOL_DIRS` 表，`path.basename` 那道防 `../` 穿越的
兜底照抄。

三个不是防御性、而是**必需**的设计：

- **封面按游戏 id 命名，不按游戏名。** 名字是可编辑字段，改一次名字就找不到自己的封面了。
- **URL 必须带 `?v=updated_at`。** 文件名由 id 推出来，同后缀换图时 URL 一个字都不变，
  浏览器会一直拿缓存 —— 用户点了「换封面」，画面毫无反应。
- **换成不同后缀时先扫一遍 `coverSiblings(id)` 清孤儿**，不然 `.png` 换 `.jpg` 会在目录里
  留一份永远不会被读到的旧图。

### 真机验证抓出来的 bug（闸门全绿也照样漏过去）

1. **详情页的失效标记在深链进入时不生效。** 失效名单是封面墙 `onMounted` 里算的，
   而模块记忆恢复的路径可能**直接落在详情页**上 —— 那时名单是空的，页面就拿
   「2026-08-28 验证过」去描述一个当下不存在的目录。修法是在 Detail 的 `onMounted` 里补一次。
   判断用新加的 `staleChecked` 标记而不是 `staleSaves.size === 0`：那个 0 有两种含义
   （「还没查」和「查过了，都在」），用 size 判断会变成「一切正常时每次进详情页都重扫一遍全库」。
2. **保留上限输入框清空后存成了 0（= 不限），而不是退回 10。** `Number('')` 是 0，
   原本那句 `Number.isFinite(n) && n >= 0` 就这么被穿透了。改成先单独挡掉空串。

## 八、环境级的坑（下次直接查这一节）

这些和业务无关，但每一个都实打实烧掉了时间。

### CDP 驱动 Electron

- **窗口被遮住时 Electron 掐掉 rAF**（`backgroundThrottling`），`<Transition mode="out-in">`
  卡在半路，**应用内跳转看起来毫无反应**（DOM 里一张卡都没有，像是页面坏了），
  而且**控制台一条报错都没有**。判据是 `document.visibilityState === 'hidden'`。
- 绕法：每个路由用 `Page.navigate` **整页加载**，走首次挂载，不经过那个过渡。
  但只改 hash 的 `Page.navigate` 是同文档跳转，**必须带一个变化的 query**（`?r=1#/game`）
  才会真的重载。
- **`window.confirm` 是真模态，不自动点掉的话 `Runtime.evaluate` 永远不返回**，
  整个驱动脚本挂死，看起来像 CDP 断了。挂 `Page.javascriptDialogOpening` +
  `Page.handleJavaScriptDialog { accept: true }` 自动确认。
  （`prompt` 在 Electron 里是空实现，`confirm` 是正常的，所以它才会真的挡住。）
- `vite-plugin-electron` 不转发 `ELECTRON_EXTRA_LAUNCH_ARGS`，`npm run dev` 开不出调试端口。
  直接 `npx electron . --remote-debugging-port=9222` 跑构建产物，顺带把 `file://` 那条路
  一起验了。
- 新 profile 会被引导页拦住，先 `settings.patch({ onboarded: true })` 再重载。
- Node 22 自带 `WebSocket`，不用装 `ws`。

### 驱动 Windows 原生文件对话框

`pickCover` 是上封面的唯一途径，绕过对话框就等于没验 `setGameCover` 那一段。
**不要用 SendKeys**，四个坑一起记：

1. **`.ps1` 没 BOM 时 PS 5.1 按 cp936 读**，文件里的中文注释/字符串被搅碎，
   连 here-string 都能解析失败（`ȱ�� using ָ��` 这种报错）。→ 驱动脚本写纯 ASCII，
   对话框**按窗口类 `#32770` 匹配**，不按中文标题。
2. **命令行参数里的中文一样会碎**（`0_0_维护` → `0_0_ά��`），路径对不上，
   对话框于是「取消」。→ 测试素材放纯 ASCII 路径（`C:\Windows\Temp`）。
3. **`FindWindow("#32770", $null)` 永不匹配。** PowerShell 把 `$null` 编排成 `""` 传给
   `string` 型参数，于是它在要求一个**空标题**的窗口。→ `lpWindowName` 声明成 `IntPtr`、
   传 `IntPtr.Zero`。
4. **SendKeys 打到的是真正有焦点的那个窗口**，而 Windows 会拒绝非前台进程调
   `SetForegroundWindow`，`WScript.Shell.AppActivate` 按 PID 也落不到 Electron 的模态子窗口上
   —— 于是「对话框找到了、路径也发出去了」，但对话框还开着、什么都没选中，
   **日志看起来完全成功**。→ 干脆不用键盘：`WM_SETTEXT` 把文件名直接写进文件名编辑框
   （`GetDlgItem(dlg, 1148)`，取不到就穿 `ComboBoxEx32 → ComboBox → Edit`），
   再给 IDOK 发 `BM_CLICK`。不需要焦点，也不抢用户正在做的事。**一次就中。**

### 补上的两处配置缺失

`electron-builder.yml` 原本已有 `appId` / `productName` / NSIS 配置，只差图标 ——

新增 `scripts/make-icons.cjs`，从 `resources/icon.svg` 生成：

```
resources/icon.png   512×512 RGBA
resources/icon.ico   16/24/32/48/64/128/256 七个尺寸，PNG 压缩条目
```

格式规定用 0 表示。生成后逐条校验过：7 个条目、偏移都在界内、每条数据都是真 PNG、
IHDR 里的宽高和目录项对得上、colorType 6（RGBA）。

（`System.Drawing` 请求 256 时返回 128 —— 那是它自己对 PNG 条目的支持限制，
不是文件缺陷，直接解析二进制确认过。）

## 十、已知的限制（不是漏洞，是取舍）

- **`search_cover` 未做**（Step 3 起就挂着的 P2）。现在封面只能手动指，没有联网找图。
- **`resetData` 只删 `kind = 'software'`**，游戏连恢复出厂都活得下来。这是 v0.5 就在的行为，
  不在 v0.6 范围内，但它意味着「清空库」对游戏模块目前是**失效的**，下一版要正面处理。
- **`dataStats` / `clearIcons` 不统计也不清封面** —— 这是故意的（封面是资产不是缓存），

- **`save_backups` 没有 `note` 列。** 加它要把 SCHEMA 6 推到 7 加迁移和回滚，换来的只是一个
  装饰性字段。保留提示里带时间和体量，用户照样判断得出该不该删；备注本身在每份
  `backup.json` 里存着。
- **罗马数字不归一**：`Final Fantasy VII` 和 `Final Fantasy 7` 在查表里是两个键。
  转换表要手工维护而且会误伤（`Warhammer 40,000` 里的 40000 不是罗马数字），
  收益是几十个条目，代价是一张谁也说不清对不对的映射表。
- **走系统 shell 兜底启动的那次跟不到时长**，`launch()` 的 message 里明说了。
- **中文名的命中率有限，且是数据源决定的。** 真索引里带中文的键 170 个，其中纯中文的只有
  49 个（一方灵田、中华三国志、克苏鲁异闻录…），这些能直接查到。另外 121 个是
  「Antarctic Girl 南極娘」这种中英混排的原名，归一之后成了 `antarcticgirl南極娘`，
  只用中文名查不到。做子串匹配能救回来，但会引入误命中，不值得。
  实测三层链路整体没问题：库里一个游戏有中文名、英文名、目录名三个键，`lookupSavePaths`
  按顺序都试，英文名通常兜得住。**原神确实查不到** —— 它压根不在 ludusavi 的收录范围里
  （启动器托管的网游），这是数据源的边界，不是查表的 bug。
- 索引里有 81 个键 ≤3 字符，查过一遍，全是正当的短英文标题（N、Q、Fe、Fez、Oni），

- **模块切换栏的「N 个待确认」角标对游戏永远不亮**（游戏识别不走暂存面板，见 Step 3 偏离）。

- **不做后台游玩监控**：用户直接双击 exe 玩的不记时长。
