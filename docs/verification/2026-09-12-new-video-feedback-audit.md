# 新视频实测核对与优化清单 · 2026-09-12

本轮共整理 **18 项优化：6 项优先修复、9 项流程与资料完善、3 项扩展能力**。其中包含已复现的缺陷、当前功能边界和用户提出的新需求，不能都算作同一种错误。

核对依据：用户提供的九张截图、三个样本目录及复制整理后的目标目录、当前资料库的相关记录、扫描日志和实现代码。运行版本为 `0.8.0-local-structure-20260912`。本轮完成调查与统计，产品代码未修改。

## 已核实的关键事实

### 1. 新视频已经入库；导入按钮的含义不清楚

截图中的「2 个注册」「新增」「从本地 NFO 注册」都表示已经落库，不存在还要点击一次确认注册的步骤。「候选」统计的是扫描输入，与已入库数量放在一起容易误解。

当前「导入」调用的是抱一资源包导入：读取已有 `baoyi.json`，或由抱一生成的单集旁车资料重建清单；普通的 MP4、NFO 和图片目录不适用。样本目录没有抱一清单，报错已复现。

`baoyi.json` 应由应用生成、校验和维护，用户不用手写，也没有必要要求模型从零生成这种固定格式。普通目录可以由应用读取本地资料、必要时让 Agent 补齐身份，再统一写出自己的清单。界面需要明确区分普通目录导入与已有资源包导入，或提供一个能自动分流的入口。

### 2. NFO 识别、强制刮削与来源补集之间断开了

每集样本 NFO 有原名、288 字简介、5 个 genre、8 个 tag，并有分级信息。现有流程保留了片名、简介和本地封面，但登记结果中普通标签为 0，原名写成文件名解析出的 `Vol 1 25078` 等片段。该 NFO 没有当前程序可用的 Hanime 编号。

离线探针还确认：文件名本身能命中 Hanime 通道，但 `identifyOne` 在检测到 NFO 后就完成本地注册并返回，后面的分类判断和强制通道都不会执行。这解释了「按里番刮削」仍然只出现「已从 NFO 离线注册」。补集入口看到的仍是空来源编号，所以无法查到系列。

需要同时处理字段映射和来源补齐：本地 NFO 是资料来源，不能因为它存在就禁止用户明确发起的联网刮削；未绑定来源时，应提供按片名搜索并确认来源、或绑定用户给出的链接。文件名数字只作线索，不能未经匹配直接视为站点编号。

依据：[识别分支](D:/8.Project/0_0_维护/抱一/electron/kinds/video/service.ts:499)、[本地登记映射](D:/8.Project/0_0_维护/抱一/electron/kinds/video/registration.ts:74)。

### 3. “海报变空”与“选到了横图”是两个问题

本地 NFO 海报文件仍然存在，缓存中的哈希副本也存在。普通读取会转换成可由应用协议访问的缓存路径；修改类型、部分资料更新和重新刮削返回的是原始本地路径。前端只取文件名构造缓存 URL，最终访问了缓存目录中不存在的文件名。点击「找海报」再次取得正常的展示对象后，图片恢复。

另一方面，HanimeViewer 样本已有的 PNG 都是 **1024×576** 横图；NFO 样本海报是 **400×509** 竖图。目前只有一套 `coverUrl/poster_path` 用途，找海报还优先接受本地图片。已有横图便可能让网络中的另一种图片根本没有下载机会。

应分别保存竖版宣传封面和横向预览图：前者用于影视墙、作品或单集详情，后者用于作品内容区域。来源元数据中已观察到 `cover` 与 `thumbnail` 两类地址，但本轮未联网逐页核验竖图可用性，后续应按真实图片尺寸和用途判断，不能只改 URL 中的单词。

依据：[读取时的图片转换](D:/8.Project/0_0_维护/抱一/electron/kinds/video/service.ts:114)、[更新返回值](D:/8.Project/0_0_维护/抱一/electron/kinds/video/service.ts:139)、[前端图片 URL](D:/8.Project/0_0_维护/抱一/src/utils/index.ts:223)、[找海报顺序](D:/8.Project/0_0_维护/抱一/electron/kinds/video/service.ts:970)。

### 4. 共享目录的“检查文件”确实有归属错误

使用样本的两个真实文件和 NFO，在内存库登记两个独立条目后，检查第一条即可复现「目录资料指向另一作品，请核对目录归属」。无需依赖损坏的清单；样本当时根本没有 `baoyi.json`。

原因是未绑定合集目录的单条记录，检查时会退到父目录，并把相邻视频都纳入目录清单注册，随后出现多作品归属。现有保护只覆盖「文件恰好放在配置的扫描根目录」这一种情况，普通共享子目录仍会落入该路径。

应保留“单集仅拥有自身文件与附件”的边界；只有明确建立的合集目录，才允许发现并归入新内容。不能通过取消归属校验来消除报错。

依据：[检查文件入口](D:/8.Project/0_0_维护/抱一/electron/kinds/video/local-sync.ts:102)。

### 5. info.json 尚未完整转换；同名文件问题被绕过了

目前目录检查会读取 `baoyi.json`、视频同名 `.baoyi.json` 和文件名，没有解析 HanimeViewer 的 `info.json`。合成样本验证：文件叫 `info1.json` 时新增集无简介和封面；改回 `info.json` 后仍相同。因此缺口不只是文件改名。

整理后三个源 `info.json` 仍在原目录，目标目录没有复制它们。目标 `baoyi.json` 保存的是已经登记到库里的标准化字段，包括各集标题、简介、来源和文件路径；它不是原始 `info.json` 的完整备份。当前单集结构还没有标签字段，不能说站方全部资料已经按集完整保留。

`.nomedia` 在样本中都是 0 字节，是目录标记，无需按每集拼接成 JSON。可按目录保留一个标记；`info.json`、NFO、字幕、图片则要依据标题、来源编号及文件关系分别归属，保留原始资料时使用不冲突的名称或独立元数据目录。

目标目录中还存在每集 `UUID.png` 与视频同名 `.poster.png` 内容完全一致的副本。说明生成清单、单集资料、简介和图片的策略需要统一，减少重复产物。

依据：[本地新增项解析](D:/8.Project/0_0_维护/抱一/electron/kinds/video/local-files.ts:52)、[整理文件收集](D:/8.Project/0_0_维护/抱一/electron/kinds/video/organize.ts:243)。

### 6. 手动删视频会留下“缺失”记录；当前缺少单集移除操作

样本 `407946` 当前第 2 集文件已经不存在，库和清单仍保留其来源与内容项。这是现有的缺集追踪行为，检查文件不会自动把资料也删掉。真正缺的是明确的单集操作入口。

需要区分：保留为待补齐、仅移除库内记录、移出合集，以及连同本地文件一起删除。涉及共享附件、多个版本和后续重扫时，要保证移除结果可预期；不能让“检查文件”隐式代替删除。

### 7. 重扫没有重复卡片，但重复消耗了模型调用

最新三条重扫日志分别为 **20,029、20,170、21,203 tokens，合计 61,402**；每条都重新执行 `hanime_search → hanime_detail → register_video`。当前库保留一个有效合集与归档的原条目，没有重新生成三个独立有效作品。

去重发生在登记阶段，识别阶段没有提前跳过。当前 prompt 已有同目录条目提示，但未把“已经合入哪个合集、哪些文件或资料未变化”作为确定性的跳过条件。

建议在进入 Agent 前，通过文件身份、来源编号、已有归属和变化状态判断：普通重扫跳过已完成且未变化的内容，只对新增或有变化的内容补资料；用户明确点击重新刮削时才强制重取。给 Agent 的已有条目摘要仍有价值，但不能只依赖一句提示词省 token。

依据：[当前识别循环](D:/8.Project/0_0_维护/抱一/electron/kinds/video/service.ts:431)、[已有条目提示](D:/8.Project/0_0_维护/抱一/electron/kinds/video/prompts.ts:385)、[归属复用](D:/8.Project/0_0_维护/抱一/electron/kinds/video/registration.ts:34)。

## 18 项优化列表

P1 为优先修复的识别、展示、归属和性能问题；P2 为日常流程及资料完善；P3 是依赖前两部分的扩展操作。

| 编号 | 优先级 | 优化项 | 核对结论与验收目标 |
| --- | --- | --- | --- |
| 01 | P2 | 普通目录导入与资源包入口 | 普通目录不能报一个没有后续操作的缺清单错误；应用自动分流，或清楚命名并引导扫描；清单由应用维护 |
| 02 | P2 | 扫描结果与任务统计 | 清楚显示已入库、新增、更新、跳过、失败，区分候选输入；同时纠正以本轮累计注册数判断单项成功的日志逻辑 |
| 03 | P1 | NFO 字段和类型识别 | 保留 NFO 原名、分类线索、标签等，避免把文件名解析残片当原名；里番分类不被本地离线分支绕过 |
| 04 | P1 | 强制刮削与来源绑定 | 强制按里番刮削真正匹配来源；无来源作品可搜索确认或填链接，绑定完成后能够补集 |
| 05 | P1 | 更新后本地海报失显 | 读、写、刮削返回的图片均可访问；不再需要反复点击找海报 |
| 06 | P1 | 单文件及共享目录检查 | 检查单条只作用于自己的文件；合集按明确归属发现新增；复现样本不再报错误归属 |
| 07 | P1 | 新增本地集的资料识别 | 能读取并匹配 NFO、HanimeViewer JSON、图片；新增集得到属于自己的简介、封面和来源，不借用相邻集的资料 |
| 08 | P2 | 单集资料及刮削入口 | 每集可独立刮削、编辑资料和选图；完整保存原名、简介、标签及来源，操作不改其他集 |
| 09 | P2 | 单集移除与删除 | 提供保留缺集、移出合集、移除记录及可选删除本地内容的明确操作，兼顾版本和共享附件 |
| 10 | P2 | 第三方附件与同名处理 | 标准化信息和原始资料分别保留；info.json、NFO、字幕、图片按单集归属，.nomedia 按目录处理；复制预览列出实际处理方式 |
| 11 | P2 | 本地资料产物整理 | 统一清单、单集旁车、简介、图片和备份的放置规则；同一图片不在目标目录重复生成多个无意义副本 |
| 12 | P2 | 竖版封面与横向预览双图 | 分开抓取、缓存、保存和展示两种图片；支持手动选择与明确回退，已有横图不阻止补取竖图 |
| 13 | P2 | 收藏分组仅由用户管理 | 取消 Agent 和刮削的自动分组写入；来源系列关联另存，不据此自动创建单条目收藏分组 |
| 14 | P2 | 收藏分组直接编辑 | 点击当前分组即可改名、选已有分组或清空，不再依赖整页编辑模式 |
| 15 | P1 | 重扫前去重与增量识别 | 已入库且未变化的文件在调用 Agent 前跳过；明确报告“已在某合集，未重新识别”；有变化才处理 |
| 16 | P3 | 批量管理 | 多选后批量设分组、增加/移除标签、删除；删除可选择是否处理本地内容，并列出影响范围 |
| 17 | P3 | 合集整理支持剪切 | 增加移动选项；同盘移动和跨盘迁移都要更新路径、清单与任务，处理同名冲突并可恢复中断 |
| 18 | P3 | 首页合集展开及单集标签检索 | 延续上轮需求：默认合集展示，可展开单集；按标签返回实际命中的单集，合集汇总标签不冒充全部单集共有标签 |

## 建议实施顺序

1. **修通识别与来源**：03、04、06、07、15。优先让本地资料丰富和资料较少的样本走一致的身份登记流程，并避免重复调用模型。
2. **修复图片展示并完善单集资料**：05、08、12、18。区分稳定的图片访问与双图选择，补足单集标签后接入筛选和展开。
3. **统一本地资料与整理**：10、11、09、17。先明确文件与附件归属，再加入删除和剪切，避免放大现有边界问题。
4. **收尾日常操作**：01、02、13、14、16。精简入口、结果反馈与分组操作，批量操作复用已经稳定的单项能力。

上述是依赖顺序；P1 项可先集中交付，扩展操作不必阻塞基础修复。

## 已实测可用的部分

按用户反馈：普通 NFO 的基本登记与本地简介读取可用；HanimeViewer 命名的来源识别可用；已有来源的缺集下载成功；单集组建合集、加入已有合集、复制整理均已走通。这些行为在优化时需要继续保留。

“没有重复条目”“手动删文件后保留缺失项”也有当前机制可解释；需要优化的是前者的调用成本与日志，后者的单集管理入口。
