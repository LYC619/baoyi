# 批量整理时的界面卡顿修复

修复包：`release/0.8.0-video-agent-background-20260913/win-unpacked/抱一.exe`。
退出旧版后运行这个目录内的程序，继续使用原资料库。调试和回归使用独立资料库及虚构视频；正式资料库仅做只读诊断。

## 原因

每次整理进度更新会逐个通知源作品，影视首页收到每条通知都立即刷新整库。旧列表读取会重新检查文件、改写资产检查时间，并为每部作品重复解析整理历史。连续通知把主进程占住，窗口在切换或恢复时便可能长时间无法响应。用户稍后反馈界面自行恢复；正式任务记录也显示该轮已结束，其中 126 项完成，1 项补资料未完成。

预览阶段还存在整批同步计算的问题，一并改为每组合集之间处理待办的窗口事件和取消请求。

## 变更

- 合并列表及统计请求；查询期间的变化只保留最后一次刷新，旧查询不覆盖新筛选结果。
- 影视首页的更新通知合并 150 毫秒，隐藏时先记录变化，显示时再刷新；离开页面清理监听和计时器。
- 列表使用轻量资料快照，不改写资料库或反复读取整理历史；最多 8 个异步文件检查，继续实时区分可用、缺失和未下载内容。
- 封面异步缓存，未变化的图片不重复读取和计算摘要；缓存丢失时重新生成。
- 合并后按实际剩余作品计算补资料任务总数，逐项更新进度，处理结束到 100%，取消时保留真实完成量。

## 对照实测

使用同一套 137 部虚构作品、146 个小型测试文件、29 个待合并系列，在真实 Electron 修复包中执行。此耗时用于比较界面刷新开销，不代表真实大视频的搬移速度。

| 场景 | 旧包 | 修复包 |
| --- | ---: | ---: |
| 40 条连续通知引发的整库查询 | 40 次 | 1 次 |
| 该轮列表读取总耗时 | 16,925 毫秒 | 9 毫秒 |
| 列表同步文件检查 | 44,560 次 | 0 次 |
| 该轮主线程心跳最大延迟 | 17,078 毫秒 | 14 毫秒 |
| 29 组小文件实际移动（含窗口切换测试） | 78,689 毫秒 | 15,207 毫秒 |

后台窗口测试 6/6 通过：隐藏期间通知合并、重新显示后刷新、执行中最小化和恢复、切到设置页再返回、29 组各执行一次、完成进度与窗口响应。该次整个测试的最大心跳延迟为 652 毫秒，未观察到 renderer 错误或无响应事件。所有 146 条单集简介和观看进度保留，68 个候选视频移入合集目录。

证据：`output/video-agent-background-20260913/baseline/evidence.json`、`native/evidence.json` 及相同目录内的恢复和完成截图。测试关闭了 Playwright 自带的“始终可见”模拟，以核实实际窗口隐藏行为；产品没有禁用 GPU 或全局修改后台节流。
